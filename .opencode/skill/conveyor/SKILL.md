# Конвейер спринтов

Конвейер исполняет цикл спринта в текущей сессии OpenCode. Кода нет:
оркестратор — основная сессия, фазы — субагенты с инструкциями из раздела
«Роли», состояние — файл спринта и git. Гейт каждой фазы оркестратор
записывает в файл спринта («Ход фаз»).

## Запуск

Только по явной команде владельца («через конвейер», «запусти конвейер»).
Без неё спринт идёт в чате как обычно. Команда старта — разрешение на
весь цикл; отдельного «разрешения на анализ» не спрашивать.

## До старта — правила проекта

Конвейер работает по правилам проекта, в котором запущен:

1. Прочитать правила ассистента проекта (AGENTS.md / CLAUDE.md в корне),
   доску задач (бэклог, направление, список спринтов) и журнал
   оркестратора, если проект его ведёт — точку входа `handoff.md` читать
   первой.
2. Взять из них: формат файла спринта, команду проверки, правила git и
   пуша, правило чистовика («одно решение — один файл»).
3. Правил нет — спросить владельца, не выдумывать.

Диалект файла спринта по умолчанию (если в проекте не задан): заголовок
`### Спринт N: …`, `Цель:` одной фразой, `## Задачи` чекбоксами,
`## Проверка владельцем`, `## Анализ перед стартом`, `## Ход фаз`,
`## Итоги и ретро`.

## Цикл

Фазы по порядку, каждая закрывается своим гейтом; после каждой
оркестратор пишет в «Ход фаз», чем фаза закончилась.

1. **Планирование** — субагент «планировщик»: собирает состав из
   направления и бэклога, пишет файл спринта и «Анализ перед стартом».
   Гейт: команда старта владельца дана; состав в рамках направления
   отдельного согласования не требует. Стопы: направление пусто или
   исчерпано; задача опрокинута анализом; всплыл выбор уровня концепции —
   вопрос владельцу.
2. **Реализация** — субагент «реализатор»: задачи по чекбоксам, решения
   до кода, чистовик, коммиты по ходу. Гейт: все задачи отмечены, команда
   проверки зелёная — вывод в файл спринта.
3. **Приёмка** — субагент «приёмщик»: критерии задач, пары «обещано —
   сделано» из анализа, чистовик против кода, свой прогон проверки. Гейт:
   вердикт ACCEPT. REJECT — правка реализатором; третий REJECT подряд —
   вопрос владельцу.
4. **Закрытие** — субагент «закрывающий»: итоги и ретро, строка в список
   спринтов, финальная проверка → коммит закрытия → пуш → посмотреть ран.
   Гейт: проверка зелёная, пуш выполнен, ран зелёный.

## Гейт

Команда проверки проекта — обязательный гейт реализации, приёмки и
закрытия. Красный вывод — в файл спринта, фаза не закрывается. Зачесть
проверку можно только прогоном: итоги фазы называют команду и её
результат (числа тестов), не «зелёно» голословно.

## Роли

Оркестратор запускает роль субагентом: передаёт текст роли из этого
раздела, файл спринта и указание прочитать правила проекта.

### Планировщик

Субагент фазы планирования. Собирает состав спринта сам, но строго в
рамках направления проекта: источник задач — цели направления и бэклог,
придумывать задачи вне них нельзя.

Делает:

1. Берёт следующую цель направления; целей нет или исчерпаны — вопрос
   владельцу.
2. Разбирает цель на задачи: одна задача — один проверяемый итог; рядом
   берёт задачи высшего приоритета бэклога, которые укладываются.
3. Пишет файл спринта в диалекте проекта: заголовок, «Цель:», задачи
   чекбоксами, «Проверка владельцем» (показ и живая проверка для всего,
   чего не проверяет автоматика), «Анализ перед стартом» (по каждой
   задаче — почему разумна, что проверить до кода), «Ход фаз», «Итоги и
   ретро» пустым.
4. Фиксирует состав в git.

Гейт: команда старта владельца дана — без неё роль не запускается; состав
в рамках направления отдельного согласования не требует.

Стоп-условия (вопрос владельцу): направление пусто или исчерпано; задача
опрокидывается анализом; всплыл выбор уровня концепции (деньги, внешние
сервисы, чувствительные данные).

### Реализатор

Субагент фазы реализации. Делает задачи файла спринта по чекбоксам,
сверху вниз, не больше 1–2 в работе.

Правила:

- «Анализ перед стартом» — исполнить до первого кода: чистый —
  продолжать; опрокинул хотя бы одну задачу — полный стоп, вопрос
  владельцу.
- Решения — до кода, по правилам проекта: рекомендация с главным
  trade-off'ом, источник рядом с решением, фиксация в чистовике до кода.
- Критерии задач закрываются утверждениями: «E2e: …» — проверкой в
  команде проверки проекта, story — в Storybook-тестах, а не показом.
- Коммиты по ходу — локально, понятными сообщениями со словом «Спринт N».

Гейт: все задачи отмечены, команда проверки зелёная; хвост вывода — в
файл спринта.

Стоп-условия (вопрос владельцу): решение уровня концепции; анализ
опрокинул задачу; способ реализации расходится с принятым стандартом или
стандарт устарел.

### Приёмщик

Субагент фазы приёмки. Ревьюит итог реализации против файла спринта и
чистовика; сам ничего не правит, находки — задачами.

Проверяет:

1. Каждую задачу — против её критерия в файле спринта; критерий
   «E2e: …» закрыт явной проверкой в команде проверки проекта, а не
   story.
2. Пары «обещано — сделано» из «Анализа перед стартом»; расхождение —
   замечанием.
3. Чистовик против кода и итогов: формулировки окончательные, без
   «возможно»; один факт — один файл; у новых утверждений о поведении
   платформ — источник.
4. Пути возврата и отмены (обрыв жеста, отказ сети, восстановление) — у
   каждой задачи с жестом, сетью или оптимистичной записью.
5. Прогоняет команду проверки сам — зелёная часть гейта приёмки.

Итог: вердикт ACCEPT или REJECT с перечнем замечаний; находки — задачами
в бэклог с глаголом и приоритетом (высший — «Из проверки спринта N»).
Вердикт и находки — в файл спринта.

Третий REJECT подряд — вопрос владельцу.

### Закрывающий

Субагент фазы закрытия. Сводит итоги и закрывает спринт по правилам
проекта.

Делает:

1. «Итоги и ретро» в файле спринта: что сделано (со ссылками на
   чистовик), что мешало, что всплыло — задачами в бэклог.
2. Решения уровня концепции — строкой в журнал решений проекта.
3. Строку в список спринтов: «- [Спринт N: …](NN-…md) — …. Закрыт
   ДД.ММ.ГГГГ.»
4. Финальный прогон команды проверки — зелёная.
5. Коммит закрытия → пуш → посмотреть ран. Красный ран — в файл спринта
   и вопрос владельцу.

Гейт: проверка зелёная, пуш выполнен, ран зелёный.

## Методология спринтов

Спринт — не отрезок календарного времени, а пронумерованная пачка задач
с целью. Дат нет намеренно: привязка к неделям превращает доску в отчёт о
фиктивном темпе. Соло-проект — без лишних ролей и церемоний, только
явные границы «что делаем сейчас».

### Доска

- **Бэклог** — весь пул задач без привязки ко времени. Метки
  `P0`/`P1`/`P2` перепроверяются на сверке: закрылся внешний блокер — то,
  что стояло за ним с `P2`, могло стать `P1`.
- **Файл спринта** — один на спринт, `NN-краткое-описание.md`, плюс
  строка в списке спринтов доски. После закрытия остаётся историей: не
  удаляется и не переносится.
- **В работе** — задачи внутри файла текущего (последнего по номеру)
  спринта. Не больше 1–2 одновременно, чтобы не размазываться.
- **Выполнено** — задачи отмечены в файле спринта; итоговое решение
  уходит в чистовик, на доске остаётся короткая запись со ссылкой:
  доска — про статус, не про содержание решений.

Всё, что всплыло (в диалоге, в коде, где угодно), попадает в бэклог
сразу, а не остаётся «в уме»; горит и укладывается в цель спринта —
сразу в файл текущего спринта.

### Полный цикл одного спринта

состав согласован в диалоге → фиксация файлом `NN-*.md` и строкой в
списке спринтов → **команда старта от владельца** (фиксация состава
разрешением на работу не является) → «Анализ перед стартом» до первого
кода → работа и проверка на локалхосте, сверка по ходу → все задачи
отмечены, команда проверки зелёная → **коммит закрытия** → **пуш** →
посмотреть ран → обсуждение состава следующего спринта сразу, не
откладывая. Живая проверка и показ — в очереди проверок владельца, вне
цикла.

### Состав спринта

- В чате состав следующего спринта не придумывать самостоятельно:
  сначала обсудить и согласовать с владельцем, потом фиксировать.
  Прозвучала команда старта, а состав не согласован — начать с обсуждения
  состава, а не придумывать задачи.
- Конвейером состав собирает планировщик сам, строго в рамках целей
  направления и задач высшего приоритета бэклога (раздел «Роли»).
- Состав — столько задач, сколько реально сделать за один присест, не
  больше.

### Анализ перед стартом

До любого кода, по каждой задаче:

- задача разумна и не навредит проекту дальше;
- где есть выбор способа реализации (технология, UX-паттерн, архитектура)
  — поискать, как эту проблему решают другие;
- по затронутым библиотекам — просмотреть актуальную документацию (API,
  версии, ограничения), а не полагаться на память.

Чисто документационная или юридическая задача — одна строка в заметке,
без ритуального «ресёрч не требуется». Результаты — в диалог и короткой
заметкой «Анализ перед стартом» в файле спринта; задача, добавленная на
ходу, проходит ту же проверку в лёгкой форме до кода по ней.

- Анализ чистый или меняет только способ реализации внутри согласованного
  скоупа — продолжать, взяв лучший вариант.
- Анализ опрокинул хотя бы одну задачу (убрать, разбить, существенно
  расширить, либо всплыло решение уровня концепции — деньги, внешние
  сервисы, чувствительные данные) — **полный стоп всего спринта**, даже
  если остальные задачи чистые: правка состава с владельцем, потом новая
  команда старта.

### Сверка

Короткий проход по доске перед началом новой пачки работы: что сделано —
отметить в файле спринта; что берём в работу дальше — обновить там же;
приоритеты бэклога — перепроверить по текущим блокерам, чтобы метки не
протухали; что новое всплыло — сразу задачей в бэклог, а если горит и
укладывается в цель спринта — сразу в файл текущего спринта. Смысл
сверки — не дать новым задачам потеряться и не копить их «в уме».

### Обзор и ретро

В конце спринта: сделанное — короткой ссылкой на раздел чистовика прямо
в файле спринта; несделанное — обратно в бэклог (или явно в следующий
спринт, если это по-прежнему приоритет); при необходимости — короткая
заметка в самом файле спринта: что мешало, что стоит изменить в
следующем.

### Живая проверка владельца

Обязательна и идёт **после пуша, не до**. Спринт, трогающий то, что
автоматикой не проверяется в принципе (нативные диалоги, тач-жесты,
поведение реального клиента, физические устройства), заводит её пунктом
«Проверка владельцем» с первого дня, а не «допишем в конец» — иначе
проверка уезжает невыполненной. Закрытие она не держит: пункт остаётся
неотмеченным, пока владелец не прогнал сценарий руками. Пока прода нет —
проверка идёт на prod-сборке по локальной сети.

Синтетические события в тестах (длинное нажатие как событие контекстного
меню, системный диалог как синтетическое событие установки): рядом с
проверкой тест называет подмену, а спринт заводит пункт проверки
настоящего жеста. Повторённая молча, подмена разъедает доверие к сьюте;
названная — становится явной дырой в очереди проверок.

### Показ новых компонентов

Сначала темплейт, потом приложение: новый компонент заводится
изолированным рендером (Storybook или аналог) и показывается владельцу
живьём. Показ работу не держит: компонент идёт в приложение, показ
встаёт в очередь проверок владельца, замечания — задачами `P0`. Перебор
вариаций умолчанием не является — только по явному запросу владельца,
когда выбор действительно нужен.

### Пуш — шаг закрытия

Пуш почти всегда давался без дополнительных проверок, а ожидание команды
держало закрытый спринт. Trade-off: момент запуска пайплайна выбирает
доска, а не владелец; с деплоем это автодеплой. Действующий порядок:

1. Все задачи отмечены, команда проверки зелёная → коммит закрытия →
   пуш в `main` → посмотреть ран. Красный CI — на прод не уехало ничего;
   следующий спринт не начинается, пока ран не зелёный.
2. Разработка и проверка идут на локалхосте. Пуш посреди спринта —
   только по явной команде владельца; пуш ради «посмотреть, как
   выглядит» не делается никогда.
3. Приватный репозиторий — статус рана читается только авторизованным
   `gh` (`gh run list`, `gh run view --log-failed`). `gh` не авторизован
   — не повод пропустить шаг, а повод авторизоваться.
4. Что автоматикой не проверяется в принципе — проверяет владелец
   руками, после того как код уехал; пока прода нет — на prod-сборке по
   локальной сети.

### Направление

Цели, в рамках которых планировщик конвейера собирает следующий спринт.
Пишет и меняет владелец; планировщик только читает. Цель достигнута —
строка уходит; список пуст — конвейер останавливается и спрашивает.
Раздел «Не брать» перечисляет темы, требующие выбора провайдера или
продуктового решения до кода: планировщик их в состав не берёт. По пути
— `P0`/`P1` бэклога, если укладываются в спринт рядом с целью.

### Диалект файла спринта

Диалект по умолчанию из «До старта» в развёрнутом виде (проект может
задать свой):

```
### Спринт N: короткое описание

Цель: одна фраза — что должно быть верно к завершению спринта.

## Задачи
- [ ] Задача. Один проверяемый итог на задачу; критерии — внутри
      задачи, утверждениями, закрываемыми автоматикой.

## Проверка владельцем
- [ ] Показ или живая проверка: что показать и как прогнать.

## Анализ перед стартом
(по каждой задаче — почему разумна, что проверить до кода; сюда же —
решения владельца на планировании, с источниками и trade-off'ами)

## Ход фаз
(оркестратор пишет сюда гейт каждой фазы)

## Итоги и ретро
```

- Показ новых компонентов и живая проверка — разделом «Проверка
  владельцем», не в списке задач.
- Критерии задач закрываются утверждениями: «E2e: …» — проверкой в
  команде проверки проекта, story — в Storybook-тестах, а не показом.
- Решения, принятые владельцем на планировании, фиксируются до кода — в
  чистовике и в «Анализе перед стартом» (пример из опорного проекта:
  почтовый провайдер и механизм сессий решены на планировании спринта,
  зафиксированы в `stack/`, с источниками и главным trade-off'ом).

## Методология документации

Документация проекта — **чистовик**: только принятые решения,
формулировки окончательные, без «возможно» и альтернатив. Идёт
обсуждение — значит место в задаче бэклога, а не в основном тексте.

### Структура

- `concept/` — продукт: что делает и для кого, бизнес-правила, скоуп,
  продуктовое поведение.
- `stack/` — как построено: стек и версии, схема данных, авторизация,
  инфраструктура, деплой, выбор провайдеров, грабли.
- `design/` — как выглядит и ведёт себя: токены, типографика, паттерны
  экранов и компонентов, UX-правила.
- `tasks/` — доска: правила воркфлоу и список спринтов, файл на спринт,
  бэклог, milestones (закрытые решения концептуального уровня).

У каждого раздела — ровно одно оглавление, перечисляющее его файлы.
(Пути по умолчанию; проект задаёт свои — скилл читает их из правил.)

### Один факт — один файл

Факт живёт ровно в одном файле-хозяине; в остальных местах — ссылка, не
копия. Правило разбиения механическое: один `##`-раздел — один файл,
новый раздел — новый файл плюс строка в оглавлении. Файл на четыре
строки — нормально; правило, требующее каждый раз решать «достаточно ли
тема крупная», — нет. Одно решение часто имеет две стороны: продуктовая
формулировка — в `concept/`, реализация — в `stack/`, между ними ссылка.
Дублировать содержание не нужно.

### Правило сжатия

Отменённое или пересмотренное решение не остаётся в чистовике
исторической сноской — уходит строкой в milestones («что было, чем
заменено, каким спринтом») и из чистовика вычищается. Чистовик отвечает
на вопрос «как есть», а не «как менялось». Без правила он растёт линейно
и перестаёт читаться целиком.

### Незакрытые темы

Незакрытая тема живёт задачей в бэклоге, в том числе связным рассуждением
на страницу. Отдельный файл-черновик допустим только под одну почти
дозревшую тему: несёт правило переезда в своей шапке и сворачивается в
чистовик, когда тема закрыта.

### Воркфлоу решений

Открытый вопрос по продукту, стеку или дизайну:

1. Не перечислять варианты — давать рекомендацию с обоснованием и явным
   главным trade-off'ом. Решение всё равно за владельцем.
2. Где решение не чистый вкус, а опирается на общепринятую практику
   (доступность, тач-таргеты, паттерны форм, поведение библиотеки) —
   свериться с источником, а не придумывать цифры по памяти. Источник
   называется в чистовике рядом с решением.
3. Решение принято в диалоге — сразу фиксировать в чистовике: дата,
   обоснование, источник, главный trade-off. До кода, не после.
4. Решение предварительное (например, цена, которую ещё пересчитают) —
   фиксировать, но явно помечать как рабочий ориентир, а не финал.
5. Отметить в файле текущего спринта; концептуального уровня — плюс
   строка в milestones; всплыли следующие шаги — завести в бэклог.

### Решения уровня концепции

Решения, которые меняли направление проекта, и решения, отменённые по
правилу сжатия, — строкой в milestones: «что было, чем заменено, каким
спринтом, дата». Сюда же строку добавляет «Закрывающий» при закрытии
спринта.

## Состав скиллов — требования и зависимости

Состав скиллов, на который опирается конвейер в опорном проекте
(toodoo/clout-cloud): проектный скилл и глобальные скиллы
fullstack/devsecops, доступные сессиям проекта (в опорном проекте живут в
`~/.agents/skills/`). Роль подключает скилл, когда работа попадает в его
зону; оркестратор передаёт имя скилла субагенту явно, а не надеется на

### Правила компоновки

- Скиллы не подключаются «на всякий случай»: каждая роль зовёт только
  скиллы своей зоны; находки идут обычным путём — задачами в бэклог с
  глаголом и приоритетом.
- Сканы безопасности не заменяют гейт: гейт — команда проверки проекта,
  скан — дополнение приёмки для security-чувствительных спринтов.
- Скиллы безопасности запускаются только по явному запросу владельца —
  сам конвейер их в работу не ставит без него.
- Скилл из состава в проекте отсутствует или сломан — не выдумывать
  замену: работать по правилам проекта и отметить владельцу (то же
  правило, что для любых правил).

## Автономный запуск

Одна сессия OpenCode в tmux; сессия — и есть состояние конвейера,
отдельного state-файла нет.

```bash
tmux new-session -d -s conveyor \
  'opencode run --session ses-conveyor -m <провайдер>/<модель> --auto "запусти конвейер"'
```

- ID сессии обязан начинаться с `ses` — иначе `opencode run` отклоняет.
- Модель задавать явно (`-m`): без неё `opencode run` берёт бесплатную
  модель-умолчание, а не провайдера из конфига.
- Вопрос владельцу: оркестратор пишет вопрос в файл (например,
  `.conveyor/question.md`), шлёт уведомление, если в проекте есть тост,
  и завершает ход. Ответ продолжает ту же сессию:

```bash
opencode run --session ses-conveyor "ответ владельца: …"
```

- Пока конвейер работает, в проекте не запускать свои проверки и превью,
  если порты или базы общие.

## Сбои

Сетевая ошибка субагента — повторить фазу с той же точки входа; повтор не
чинит — стоп с уведомлением и вопросом владельцу. Сессия переживает сон
машины; после пробуждения — «продолжи».

## Очередь проверок владельца

Неотмеченные пункты «Проверка владельцем» всех файлов спринтов копятся и
проходятся пачкой: поднять рабочую сборку проекта, показать список, пункт
прошёл — отметить обычным коммитом, замечания — задачами высшего
приоритета «Из проверки спринта N» в бэклог.

## Журнал оркестратора

Оркестратор ведёт журнал в доске задач проекта (отдельная папка, если
проект её не определяет — `docs/tasks/conveyor-log/`): `handoff.md` —
точка входа с текущим состоянием (читается первой в каждой сессии,
обновляется при каждой смене состояния), `NN.md` — журнал спринта. Пишет
по ходу: фазы, гейты, вопросы владельцу, стопы. Так работу продолжает
любая сессия, а не только та, что начинала цикл.

# Конвейер спринтов

Конвейер исполняет цикл спринта в текущей сессии OpenCode. Кода нет:
оркестратор — основная сессия, фазы — субагенты с инструкциями из раздела
«Роли», состояние — файл спринта и git. Гейт каждой фазы оркестратор
записывает в файл спринта («Ход фаз»).

## Запуск

Только по явной команде владельца («через конвейер», «запусти конвейер»).
Без неё спринт идёт в чате как обычно. Команда старта — разрешение на
весь цикл; отдельного «разрешения на анализ» не спрашивать.

## До старта — правила проекта

Конвейер работает по правилам проекта, в котором запущен:

1. Прочитать правила ассистента проекта (AGENTS.md / CLAUDE.md в корне),
   доску задач (бэклог, направление, список спринтов) и журнал
   оркестратора, если проект его ведёт — точку входа `handoff.md` читать
   первой.
2. Взять из них: формат файла спринта, команду проверки, правила git и
   пуша, правило чистовика («одно решение — один файл»).
3. Правил нет — спросить владельца, не выдумывать.

Диалект файла спринта по умолчанию (если в проекте не задан): заголовок
`### Спринт N: …`, `Цель:` одной фразой, `## Задачи` чекбоксами,
`## Проверка владельцем`, `## Анализ перед стартом`, `## Ход фаз`,
`## Итоги и ретро`.

## Цикл

Фазы по порядку, каждая закрывается своим гейтом; после каждой
оркестратор пишет в «Ход фаз», чем фаза закончилась.

1. **Планирование** — субагент «планировщик»: собирает состав из
   направления и бэклога, пишет файл спринта и «Анализ перед стартом».
   Гейт: команда старта владельца дана; состав в рамках направления
   отдельного согласования не требует. Стопы: направление пусто или
   исчерпано; задача опрокинута анализом; всплыл выбор уровня концепции —
   вопрос владельцу.
2. **Реализация** — субагент «реализатор»: задачи по чекбоксам, решения
   до кода, чистовик, коммиты по ходу. Гейт: все задачи отмечены, команда
   проверки зелёная — вывод в файл спринта.
3. **Приёмка** — субагент «приёмщик»: критерии задач, пары «обещано —
   сделано» из анализа, чистовик против кода, свой прогон проверки. Гейт:
   вердикт ACCEPT. REJECT — правка реализатором; третий REJECT подряд —
   вопрос владельцу.
4. **Закрытие** — субагент «закрывающий»: итоги и ретро, строка в список
   спринтов, финальная проверка → коммит закрытия → пуш → посмотреть ран.
   Гейт: проверка зелёная, пуш выполнен, ран зелёный.

## Гейт

Команда проверки проекта — обязательный гейт реализации, приёмки и
закрытия. Красный вывод — в файл спринта, фаза не закрывается. Зачесть
проверку можно только прогоном: итоги фазы называют команду и её
результат (числа тестов), не «зелёно» голословно.

## Роли

Оркестратор запускает роль субагентом: передаёт текст роли из этого
раздела, файл спринта и указание прочитать правила проекта.

### Планировщик

Субагент фазы планирования. Собирает состав спринта сам, но строго в
рамках направления проекта: источник задач — цели направления и бэклог,
придумывать задачи вне них нельзя.

Делает:

1. Берёт следующую цель направления; целей нет или исчерпаны — вопрос
   владельцу.
2. Разбирает цель на задачи: одна задача — один проверяемый итог; рядом
   берёт задачи высшего приоритета бэклога, которые укладываются.
3. Пишет файл спринта в диалекте проекта: заголовок, «Цель:», задачи
   чекбоксами, «Проверка владельцем» (показ и живая проверка для всего,
   чего не проверяет автоматика), «Анализ перед стартом» (по каждой
   задаче — почему разумна, что проверить до кода), «Ход фаз», «Итоги и
   ретро» пустым.
4. Фиксирует состав в git.

Гейт: команда старта владельца дана — без неё роль не запускается; состав
в рамках направления отдельного согласования не требует.

Стоп-условия (вопрос владельцу): направление пусто или исчерпано; задача
опрокидывается анализом; всплыл выбор уровня концепции (деньги, внешние
сервисы, чувствительные данные).

### Реализатор

Субагент фазы реализации. Делает задачи файла спринта по чекбоксам,
сверху вниз, не больше 1–2 в работе.

Правила:

- «Анализ перед стартом» — исполнить до первого кода: чистый —
  продолжать; опрокинул хотя бы одну задачу — полный стоп, вопрос
  владельцу.
- Решения — до кода, по правилам проекта: рекомендация с главным
  trade-off'ом, источник рядом с решением, фиксация в чистовике до кода.
- Критерии задач закрываются утверждениями: «E2e: …» — проверкой в
  команде проверки проекта, story — в Storybook-тестах, а не показом.
- Коммиты по ходу — локально, понятными сообщениями со словом «Спринт N».

Гейт: все задачи отмечены, команда проверки зелёная; хвост вывода — в
файл спринта.

Стоп-условия (вопрос владельцу): решение уровня концепции; анализ
опрокинул задачу; способ реализации расходится с принятым стандартом или
стандарт устарел.

### Приёмщик

Субагент фазы приёмки. Ревьюит итог реализации против файла спринта и
чистовика; сам ничего не правит, находки — задачами.

Проверяет:

1. Каждую задачу — против её критерия в файле спринта; критерий
   «E2e: …» закрыт явной проверкой в команде проверки проекта, а не
   story.
2. Пары «обещано — сделано» из «Анализа перед стартом»; расхождение —
   замечанием.
3. Чистовик против кода и итогов: формулировки окончательные, без
   «возможно»; один факт — один файл; у новых утверждений о поведении
   платформ — источник.
4. Пути возврата и отмены (обрыв жеста, отказ сети, восстановление) — у
   каждой задачи с жестом, сетью или оптимистичной записью.
5. Прогоняет команду проверки сам — зелёная часть гейта приёмки.

Итог: вердикт ACCEPT или REJECT с перечнем замечаний; находки — задачами
в бэклог с глаголом и приоритетом (высший — «Из проверки спринта N»).
Вердикт и находки — в файл спринта.

Третий REJECT подряд — вопрос владельцу.

### Закрывающий

Субагент фазы закрытия. Сводит итоги и закрывает спринт по правилам
проекта.

Делает:

1. «Итоги и ретро» в файле спринта: что сделано (со ссылками на
   чистовик), что мешало, что всплыло — задачами в бэклог.
2. Решения уровня концепции — строкой в журнал решений проекта.
3. Строку в список спринтов: «- [Спринт N: …](NN-…md) — …. Закрыт
   ДД.ММ.ГГГГ.»
4. Финальный прогон команды проверки — зелёная.
5. Коммит закрытия → пуш → посмотреть ран. Красный ран — в файл спринта
   и вопрос владельцу.

Гейт: проверка зелёная, пуш выполнен, ран зелёный.

## Автономный запуск

Одна сессия OpenCode в tmux; сессия — и есть состояние конвейера,
отдельного state-файла нет.

```bash
tmux new-session -d -s conveyor \
  'opencode run --session ses-conveyor -m <провайдер>/<модель> --auto "запусти конвейер"'
```

- ID сессии обязан начинаться с `ses` — иначе `opencode run` отклоняет.
- Модель задавать явно (`-m`): без неё `opencode run` берёт бесплатную
  модель-умолчание, а не провайдера из конфига.
- Вопрос владельцу: оркестратор пишет вопрос в файл (например,
  `.conveyor/question.md`), шлёт уведомление, если в проекте есть тост,
  и завершает ход. Ответ продолжает ту же сессию:

```bash
opencode run --session ses-conveyor "ответ владельца: …"
```

- Пока конвейер работает, в проекте не запускать свои проверки и превью,
  если порты или базы общие.

## Сбои

Сетевая ошибка субагента — повторить фазу с той же точки входа; повтор не
чинит — стоп с уведомлением и вопросом владельцу. Сессия переживает сон
машины; после пробуждения — «продолжи».

## Очередь проверок владельца

Неотмеченные пункты «Проверка владельцем» всех файлов спринтов копятся и
проходятся пачкой: поднять рабочую сборку проекта, показать список, пункт
прошёл — отметить обычным коммитом, замечания — задачами высшего
приоритета «Из проверки спринта N» в бэклог.

## Журнал оркестратора

Оркестратор ведёт журнал в доске задач проекта (отдельная папка, если
проект её не определяет — `docs/tasks/conveyor-log/`): `handoff.md` —
точка входа с текущим состоянием (читается первой в каждой сессии,
обновляется при каждой смене состояния), `NN.md` — журнал спринта. Пишет
по ходу: фазы, гейты, вопросы владельцу, стопы. Так работу продолжает
любая сессия, а не только та, что начинала цикл.
